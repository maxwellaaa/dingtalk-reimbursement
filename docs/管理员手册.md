## 1. 系统架构概览

```
钉钉客户端 (H5 微应用 /h5/)
        │
        ▼
   Nginx :80/443  ── /api/* ──►  Express 后端 :3000
        │                              │
        │                              ├── MySQL 8 (reimbursement)
        │                              ├── uploads/ 附件
        │                              └── 钉钉 Stream / Webhook
        └── 静态前端 dist/h5/
```

| 组件 | 职责 |
|------|------|
| 前端 Vue3 | 报销填单、审批待办、报表 |
| 后端 Express | 免登 JWT、预算、OA 发起与回写 |
| MySQL | 业务数据、`sys_config` 运行配置 |
| 钉钉 | 身份、OA 审批（方案 B）、工作通知 |

**审批模式**

- **B（默认生产）**：提交后创建钉钉 OA 单，Stream 回写状态  
- **A（降级）**：自研 H5 待办审批，不调用创建 OA 实例 API

## 2. 环境要求与端口

| 项目 | 要求 |
|------|------|
| Node.js | 20 LTS |
| MySQL | 8.0+（开发机可用 9.7） |
| 操作系统 | Linux 服务器（Docker）或 Windows Server / 本机 |
| 钉钉 | 企业内部应用 + OA 模板（方案 B） |

| 端口 | 服务 | 说明 |
|------|------|------|
| 3306 | MySQL | 生产 Docker 默认不映射到外网 |
| 3000 | 后端 API | 生产建议仅内网或经 Nginx 反代 |
| 8080 | Nginx 前端 | Docker `HTTP_PORT` 可改 |
| 443 | HTTPS | 生产必须（钉钉 H5 要求） |

健康检查：

- 后端：`GET /api/health` → `{ ok, phase: "P5", db: true }`
- 前端（Docker）：`GET /healthz` → `ok`

脚本：`scripts/deploy/health-check.ps1`

## 3. 首次部署

### 3.1 Docker 路径（生产服务器）

1. 复制 `cp .env.production.example .env` 并填写全部密钥  
2. `docker compose -f docker-compose.prod.yml up -d --build`  
3. 初始化：`cd backend && npm run db:init && npm run db:seed-prod`（读取 `backend/.env`）  
4. 钉钉应用首页设为 `https://你的域名/h5/`  
5. `health-check.ps1 -FrontendUrl http://localhost:8080`

### 3.2 非 Docker 路径（本机 MySQL / Windows）

1. 安装 Node 20、MySQL，创建库用户（见 P5 文档 SQL）  
2. `backend/.env` 从 `.env.example` 复制并填写  
3. `.\scripts\deploy\init-production.ps1 -EnvFile backend\.env`  
4. 后端：`npm start` 或 PM2（`deploy/ecosystem.config.cjs`）  
5. 前端：`npm run build`，Nginx 使用 `deploy/nginx.conf`（改 backend 地址为 127.0.0.1:3000）  

### 3.3 生产 seed 说明

`seed-prod.js` **不会**创建 `dev_user` 或测试项目。  
用户首次钉钉登录时自动写入 `user_account`。  
需手工或通过管理页/SQL 维护：

- `region`、`project`、`project_budget`
- `approval_flow` / `approval_flow_node`（方案 A 时）
- **角色分配**：H5「我的 → 角色分配」（总经理 / 财务C 可见）

### 3.1 角色分配（点选）

1. 用**总经理**或**财务C**账号进入应用（浏览器开发可切 `gm:C` / `finance:C`）
2. **我的 → 角色分配**
3. 搜索用户 → 点选 → 选择角色/档位/项目或片区 → **确认分配**；可单条**撤销**
4. 分配「项目经理」「财务A」会同步 `project.manager_user_id` / `finance_user_id`
5. 选「员工」会清除该用户全部角色，恢复默认仅看本人
6. **仅总经理**可分配/撤销总经理档位；财务C 不可动总经理角色

**冷启动**：第一个总经理需 SQL 写入一次（对方先钉钉登录一次）：

```sql
INSERT INTO user_role (user_id, role_code, grade, status)
SELECT id, 'gm', 'C', 1 FROM user_account WHERE ding_user_id = '<钉钉userid>' LIMIT 1;
```

之后其余人全部在管理页点选即可。

### 3.2 分步点选审批人（方案 A）

自研 H5 审批链：本项目经理 → 本项目财务 →（大额）总经理。

1. **员工提交**：无需选人，自动使用项目已配置的经理、财务
2. **经理 / 财务同意**：无需再选下一环，系统按项目自动流转（大额自动到总经理；≤5千跳过）
3. 员工端不展示 A/B/C 档位
4. 方案 B（钉钉 OA）仍走钉钉模板，不在此点选

### 3.3 项目成员与入组

1. **钉钉登录**写入 `user_account`；员工**不**自助入组
2. **我的 → 项目成员**：财务C / 总经理 / 项目经理将员工加入项目后，员工才能在填单中看到该项目
3. **我的 → 我的项目组**：仅只读查看已分配项目
4. **新建报销**：项目下拉仅显示已分配项目；未分配时提示联系财务/总经理
5. 迁移：`node scripts/migrate-project-member.js`（补充 `source` / `joined_at`）

## 4. 钉钉开放平台配置清单

### 4.1 应用基础

- [ ] 创建**企业内部应用**  
- [ ] 记录 **AppKey、AppSecret、AgentId、CorpId** → 写入 `.env`  
- [ ] H5 微应用首页：`https://<域名>/h5/`（与 `FRONTEND_URL` 一致）  
- [ ] 服务器出口 IP 白名单（若企业开启）

### 4.2 权限（开发配置 → 权限管理）

- [ ] 通讯录：成员信息读、部门信息读  
- [ ] 工作流：实例写（发起 OA）、实例读（可选）  
- [ ] 工作通知消息  

### 4.3 OA 审批模板

- [ ] 按 [P4-OA对接指南](./P4-OA对接指南.md) §2 创建字段（名称一字不差）  
- [ ] 配置审批链并**发布**  
- [ ] 复制 **processCode** → `DINGTALK_PROCESS_CODE` 或 `sys_config.dingtalk.process_code`  
- [ ] 附件控件名与 `DINGTALK_OA_ATTACHMENT_LABEL` 一致（默认「发票及凭证」）

### 4.4 事件订阅

**Stream（推荐，免公网）**

- [ ] 事件订阅 → **Stream 模式**  
- [ ] 订阅 `bpms_instance_change`  
- [ ] `DINGTALK_STREAM_ENABLED=true`  
- [ ] 后端日志出现 Stream 连接成功  

**HTTP 回调（备选）**

- [ ] 配置 Token、EncodingAESKey  
- [ ] 回调 URL：`https://<域名>/api/webhooks/dingtalk/oa`  
- [ ] 写入 `DINGTALK_CALLBACK_TOKEN`、`DINGTALK_CALLBACK_AES_KEY`

## 5. 日常运维

### 5.1 启动 / 停止 / 重启

**Docker**

```bash
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml stop
docker compose -f docker-compose.prod.yml restart backend frontend
```

**PM2**

```bash
pm2 restart reimb-backend
pm2 logs reimb-backend
```

**Windows 本机**

```powershell
cd backend
npm start
# 另开终端：cd frontend && npm run dev   # 仅开发
```

### 5.2 日志位置

| 环境 | 位置 |
|------|------|
| Docker backend | `docker compose logs -f backend` |
| PM2 | `logs/backend-out.log`、`backend-error.log` |
| Node 前台 | 终端 stdout |
| Nginx | `/var/log/nginx/access.log`（Linux） |

### 5.3 健康检查与监控

```powershell
.\scripts\deploy\health-check.ps1 -BackendUrl http://localhost:3000
```

建议监控：`/api/health` 的 `db=true`、磁盘（`uploads/`、`backups/`）、钉钉 Stream 断连告警。

### 5.4 API 用量

- 表：`dingtalk_api_usage`  
- 接口：`GET /api/api-usage`（需登录）  
- 阈值：`sys_config.api.usage.warn_threshold`（默认 8000/月）

## 6. 备份与恢复

### 6.1 脚本

| 脚本 | 作用 |
|------|------|
| `scripts/backup/mysql-backup.ps1` | mysqldump + gzip，保留 N 天 |
| `scripts/backup/mysql-restore.ps1` | 从 `.sql` / `.sql.gz` 恢复 |
| `scripts/backup/backup-uploads.ps1` | 打包 `backend/uploads/` |

环境变量（可选，写在 `.env`）：

- `BACKUP_DIR`、`BACKUP_RETENTION_DAYS`（默认 14）  
- `MYSQLDUMP_BIN`、`MYSQL_BIN`（Windows 若未加入 PATH）

**示例**

```powershell
.\scripts\backup\mysql-backup.ps1 -EnvFile backend\.env
.\scripts\backup\backup-uploads.ps1
```

### 6.2 建议频率

| 对象 | 频率 | 保留 |
|------|------|------|
| MySQL | 每日 02:00 | 14–30 天 |
| uploads | 每日或每周 | 14–30 天 |
| 恢复演练 | 每季度 | 在测试库验证 |

### 6.3 Windows 任务计划程序

1. 任务计划程序 → 创建基本任务  
2. 触发器：每天 02:00  
3. 操作：启动程序 `powershell.exe`  
4. 参数：`-ExecutionPolicy Bypass -File "F:\...\dingtalk-reimbursement\scripts\backup\mysql-backup.ps1" -EnvFile "F:\...\backend\.env"`  
5. 再建一条调用 `backup-uploads.ps1`

### 6.4 Linux cron

```cron
0 2 * * * /opt/reimb/scripts/backup/mysql-backup.sh --env /opt/reimb/.env
30 2 * * * /opt/reimb/scripts/backup/backup-uploads.sh
```

### 6.5 恢复注意

1. 停止后端（避免写入冲突）  
2. `mysql-restore.ps1 -BackupFile backups\mysql\reimbursement-xxx.sql.gz`  
3. 若需附件：解压 `backups/uploads/*.zip` 到 `backend/uploads/`  
4. 启动后端并执行 `health-check`

## 7. 审批模式切换（A / B）

### 切换到方案 A（API 超限或 OA 故障）

```sql
UPDATE sys_config SET config_value = 'A' WHERE config_key = 'approval.mode';
```

或环境变量 `APPROVAL_MODE=A` 后重启（`seed-prod` / 启动逻辑以 DB 为准时优先改 DB）。

重启后端 → 新单走 H5 待办；进行中 OA 单可继续在钉钉审完（Stream 仍可回写）。

### 切回方案 B

```sql
UPDATE sys_config SET config_value = 'B' WHERE config_key = 'approval.mode';
```

确认 `dingtalk.process_code` 有效且 Stream 正常。

### 更新 processCode

模板重建后 processCode 会变：

1. 更新 `.env` 中 `DINGTALK_PROCESS_CODE`  
2. 重启后端（启动时自动同步到 `sys_config`）  
   或：`UPDATE sys_config SET config_value='PROC-...' WHERE config_key='dingtalk.process_code';`

查询当前配置：`GET /api/config/approval`

## 8. 常见问题

| 现象 | 可能原因 | 处理 |
|------|----------|------|
| 浏览器 / 钉钉打不开 | 前端未启动或 URL 无 `/h5/` | 查 Nginx / Vite；对齐钉钉首页 URL |
| `/api/health` db=false | MySQL 未启或密码错 | 查 `DB_*`、服务状态 |
| 免登失败 | AppKey/Secret 错误或应用不可见 | 核对 `.env`、应用可见范围 |
| 提交后无 OA 单 | processCode 空或权限不足 | 查 `dingtalk_oa_mapping.sync_status`、P4 文档 |
| OA 审完状态未变 | Stream 断连 | 重启 backend；查日志 `dingtalkStream` |
| 预算不对 | 未配 `project_budget` 或释放逻辑 | 查 `budget_ledger`、科目与财年 |
| 端口占用 | 3000/8080/3306 冲突 | `netstat -ano` 换端口或停冲突进程 |
| 附件无法下载 | uploads 卷丢失 | 从 backup-uploads 恢复 |

## 9. 年度维护 SOP 要点

完整清单见 [立项落地文档-方案B主导](./立项落地文档-方案B主导.md) §5.2。每年建议 1–2 人天：

**基础设施**：系统补丁、MySQL/Nginx 小版本升级、SSL 续期、磁盘 <70%、**完整备份恢复演练**

**钉钉**：轮换 AppSecret（若疑泄露）、Stream 正常、processCode 与模板一致、API 用量 12 个月峰值、审批人离职检查

**业务**：新项目 `project` + `project_budget`、审批流节点、年度 CSV 与 ERP 对账

**应用**：`npm audit`、钉钉客户端冒烟（提交→审批→回写）、更新本手册与审批人名单

**应急切换 A**：见立项文档 §5.5（改 `approval.mode`、重启、通知审批人）

## 10. 安全

| 项 | 要求 |
|----|------|
| `.env` | **禁止**提交 Git；生产独立强密码 |
| `JWT_SECRET` | `openssl rand -base64 48` 生成 |
| MySQL | 独立业务账号、生产不用 `root123` / `reimb123` |
| HTTPS | 生产必须；回调 URL 必须 HTTPS |
| 备份文件 | 含业务与附件，存盘加密或受限目录 |
| 开发接口 | `POST /api/auth/dev-login` 仅开发使用；生产 `NODE_ENV=production` |
